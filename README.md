# Concerty - система учета концертных выступлений

Веб-приложение на Django для учета концертных выступлений: концерты,
исполнители, площадки и концертные программы. Слой доступа к данным
построен на Django ORM (ПР9), структура базы управляется миграциями.

Консольная версия ПР3 и промежуточные реализации ПР5-ПР7 сохранены
в репозитории как история развития проекта.

## Назначение

Приложение для учета концертных выступлений: регистрация концертов,
исполнителей, площадок и концертных программ, а также контроль основных
параметров предстоящих мероприятий (дата, вместимость площадки, цена
билета, возрастное ограничение).

## Целевая аудитория

- организаторы концертов и концертные директора;
- администраторы концертных площадок;
- зрители, интересующиеся афишей выступлений.

## Предметная область

Предметной областью являются концертные мероприятия. Каждый концерт
проходит на определенной площадке, в нем участвует исполнитель,
а содержание выступления определяется концертной программой. Система
учитывает даты концертов, вместимость площадок, рейтинги исполнителей
и параметры программ (продолжительность, возрастное ограничение).

## Технологии

- Python 3.13;
- Django 5.2 (маршрутизация, шаблоны, ORM, миграции, административная панель);
- SQLite: база `db.sqlite3` управляется Django ORM и миграциями;
- Bootstrap 5.3 (CDN) и собственные CSS, JS, логотип в
  `homepage/static/homepage/`;
- pytest и flake8 для проверки качества кода.

## Модели данных (ПР9)

Модели описаны в файлах `models.py` четырех приложений. Django
автоматически создает первичный ключ `id` (BigAutoField).

### Performer - исполнитель (`performers/models.py`)

Поля: `name` (CharField, 200), `genre` (CharField, 100),
`rating` (DecimalField, максимум 3 знака, 1 после запятой).
Сортировка по имени. Метод `__str__()` возвращает имя и жанр.

### Venue - площадка (`venues/models.py`)

Поля: `name` (CharField, 200), `city` (CharField, 100),
`capacity` (PositiveIntegerField). Сортировка по названию.
Метод `is_suitable_for(people_count)` проверяет вместимость.

### Program - программа (`programs/models.py`)

Поля: `name` (CharField, 200), `duration` (PositiveIntegerField, мин),
`age_limit` (PositiveIntegerField). Сортировка по названию.
Метод `is_allowed_for(guest_age)` проверяет возрастное ограничение.

### Concert - концерт (`concerts/models.py`)

Поля: `title` (CharField, 200), `date` (DateField),
`expected_guests` (PositiveIntegerField), `base_ticket_price`
(DecimalField, 10 знаков, 2 после запятой), `is_cancelled`
(BooleanField, по умолчанию `False`).

Связи с тремя справочниками описаны через `ForeignKey`:

| Поле | Связанная модель | on_delete | related_name |
|---|---|---|---|
| `performer` | `Performer` | `PROTECT` | `concerts` |
| `venue` | `Venue` | `PROTECT` | `concerts` |
| `program` | `Program` | `PROTECT` | `concerts` |

Связь «многие к одному»: у исполнителя, площадки или программы может
быть много концертов, каждый концерт ссылается на одну запись каждого
вида. `on_delete=PROTECT` запрещает удалять справочник, пока на него
ссылаются концерты, и сохраняет историю выступлений. `related_name`
дает обратный доступ: `performer.concerts`, `venue.concerts`,
`program.concerts`.

Методы модели: `get_status(today)` (запланирован / идет сегодня /
завершен / отменен), `calculate_ticket_price()` (цена с учетом рейтинга
исполнителя), `check_venue_fit()` (вместимость площадки),
`calculate_revenue()` (ожидаемая выручка), `cancel()` (отмена
с сохранением только измененного поля). Отмененный концерт площадку
не блокирует.

Все модели зарегистрированы в административной панели
(`admin.py` каждого приложения) с настройками `list_display`,
`list_filter`, `search_fields`, `list_select_related`.

## Миграции

Миграции созданы для каждого приложения и хранятся в git:

- `performers/migrations/0001_initial.py`;
- `venues/migrations/0001_initial.py`;
- `programs/migrations/0001_initial.py`;
- `concerts/migrations/0001_initial.py` (внешние ключи на три модели).

Команды:

```bash
python manage.py makemigrations --check   # проверить, что все изменения описаны
python manage.py showmigrations           # состояние миграций
python manage.py migrate                  # применить миграции к db.sqlite3
python manage.py sqlmigrate concerts 0001 # SQL конкретной миграции
```

## Перенос данных из базы ПР7

Стратегия перехода: таблицы создаются и управляются Django, исходная
база ПР7 остается источником данных. Перенос выполняется скриптом
`db/import_sqlite_to_orm.py`:

```bash
python db/inspect_source_db.py     # структура исходной базы (только чтение)
python manage.py migrate
python db/import_sqlite_to_orm.py  # перенос данных в таблицы Django
```

Скрипт читает `data/concerty.sqlite` (файл не изменяется) и через
`update_or_create()` внутри `transaction.atomic()` создает записи
моделей, сохраняя исходные идентификаторы и связи. Сначала переносятся
справочники (исполнители, площадки, программы), затем концерты,
ссылающиеся на них. Строковые даты `YYYY-MM-DD` преобразуются
в объекты `date`, числа `REAL` - в `Decimal`. Повторный запуск
обновляет совпадающие записи.

Результат переноса: 12 исполнителей, 12 площадок, 12 программ,
15 концертов.

## ORM-запросы в представлениях

Представления получают данные только через менеджеры моделей; прямых
SQL-запросов и чтения JSON в них больше нет. Использованы:

- получение наборов объектов (`objects.all()`, `order_by()`);
- получение одного объекта (`get_object_or_404()`, `get()`);
- фильтрация по одному и нескольким условиям, по полю связанной модели
  (`filter()`, `venue_id`, `date__gte`, `capacity__gte`);
- исключение записей (`exclude(pk__in=...)` при поиске свободных площадок);
- поиск (`icontains`, `Q(name__icontains=...) | Q(city__icontains=...)`);
- сортировка по одному и нескольким полям, по связанной модели
  (`order_by(sort_field, "pk")`, `venue__name`, `performer__name`);
- работа со связями (`select_related()`, обратные связи `related_name`);
- сокращенный набор полей (`values()`, `values_list(flat=True)`);
- агрегирование (`Count`, `Sum`, `Avg`, `Min`, `Max`, `aggregate()`);
- аннотирование и группировка (`annotate()`, `Count(..., filter=Q(...))`,
  `values(...).annotate(...)`);
- постраничный вывод (`Paginator`, `get_page()`, тег `{% querystring %}`).

Параметры поиска, фильтрации и сортировки, приходящие из `request.GET`,
проверяются: дата разбирается через `datetime.strptime()`, числовые
идентификаторы - через `isdigit()`, поле сортировки выбирается
из белого списка `SORT_FIELDS`, неизвестное значение заменяется
сортировкой по дате.

## Веб-интерфейс

| Адрес | Назначение |
|---|---|
| `/` | главная страница и навигация |
| `/concerts/` | список концертов: поиск, фильтры по площадке, исполнителю, статусу и дате, сортировка, пагинация |
| `/concerts/statistics/` | статистика: агрегаты, группировка по статусу, по площадкам и исполнителям |
| `/concerts/<id>/` | карточка концерта со связанными объектами и расчетами |
| `/venues/` | список площадок: поиск по названию и городу, отбор по вместимости |
| `/venues/available/` | свободные площадки на выбранную дату (отмененные концерты не учитываются) |
| `/venues/<id>/` | площадка, связанные концерты, доступность на текущую дату |
| `/performers/` | список исполнителей: поиск по имени и жанру, число концертов |
| `/performers/<id>/` | исполнитель, связанные концерты, суммарные показатели |
| `/programs/` | список программ: поиск и отбор по возрастному ограничению |
| `/programs/<id>/` | программа и связанные концерты |

Несуществующие адреса и идентификаторы возвращают страницу 404
(обработчик `homepage.views.page_not_found`). Шаблоны наследуют
`templates/base.html`, повторяющиеся фрагменты вынесены в include-файлы,
ссылки строятся через `{% url %}`.

## Запуск проекта

1. Клонировать репозиторий и перейти в его каталог.
2. Создать и активировать виртуальное окружение:

```bash
python -m venv .venv
source .venv/bin/activate
```

3. Установить зависимости:

```bash
pip install -r requirements.txt
```

4. Применить миграции:

```bash
python manage.py migrate
```

5. При необходимости перенести данные ПР7. Файл `data/concerty.sqlite`
   в репозиторий не входит, поэтому на чистом клоне сначала соберите его
   из JSON (этап ПР7), затем перенесите данные в таблицы Django:

```bash
python -m db.import_json         # JSON -> data/concerty.sqlite (схема ПР7)
python db/import_sqlite_to_orm.py  # data/concerty.sqlite -> Django ORM
```

Если файл `data/concerty.sqlite` уже есть, достаточно второй команды.

6. Запустить сервер разработки и открыть `http://127.0.0.1:8000/`:

```bash
python manage.py runserver
```

Локальная база `db.sqlite3` в git не коммитится: после клонирования
таблицы создаются миграциями. Данные можно наполнить переносом из базы
ПР7, через административную панель `/admin/` или Django shell.

## Тесты

```bash
pytest
```

Тесты разделены по слоям:

- `tests/test_orm.py` - модели, связи, CRUD-операции и ORM-запросы
  (фильтрация, поиск, сортировка, агрегирование, пагинация, PROTECT);
- `tests/test_django_views.py` - страницы веб-интерфейса, фильтры,
  сортировка, пагинация, 404 и статистика;
- остальные файлы `tests/` - сохраненная логика ПР3-ПР7 (объектная
  модель, JSON-хранилище, консольное меню, SQLite-слой).

Тесты веб-слоя работают с временной тестовой базой, создаваемой
миграциями и наполняемой из `data/*.json`; рабочая `db.sqlite3`
не изменяется.
