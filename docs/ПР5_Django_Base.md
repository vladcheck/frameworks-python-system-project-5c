3. ТЕОРЕТИЧЕСКИЕ СВЕДЕНИЯ 
3.1. Веб-приложение и протокол HTTP 
Веб-приложение – программная система, доступ к которой осуществляется через 
веб-браузер или другой HTTP -клиент. В отличие от консольного приложения,  поль-
зователь взаимодействует с веб -приложением посредством HTTP -запросов: вместо 
ввода данных через input() браузер отправляет запрос по определенному адресу, а 
программа возвращает ответ.

HTTP – протокол передачи гипертекста, стандарт обмена данными межд у кли-
ентом и сервером. Обмен строится по схеме «запрос – ответ» (рис. 2): клиент отправ-
ляет HTTP-запрос, сервер обрабатывает его и формирует HTTP-ответ. 
 
Рисунок 2 – Цикл взаимодействия с веб-приложением 
HTTP-запрос состоит из трех основных частей: 
• стартовая строка – метод, адрес и версия протокола, например GET /rooms/ 
HTTP/1.1; 
• заголовки – дополнительные сведения о запросе (Host, User-Agent, Accept и 
другие); 
• тело – передаваемые данные (у GET-запросов обычно отсутствует). 
HTTP-ответ включает: 
• стартовую строку – версию протокола и код статуса, например HTTP/1.1 200 
OK; 
• заголовки (Content-Type, Content-Length и другие); 
• тело – передаваемые данные, например HTML-страницу. 
Код статуса сообщает результат обработки запроса: 200 – успешная обработка, 
404 – страница не найдена, 500 – ошибка сервера. Для получения страниц использу-
ется метод GET, для отправки данных на сервер – метод POST. 
В рамках ПР5 необходимо реализовать ба зовый цикл URL → view → response: 
обращение по определенному адресу должно приводить к формированию и возврату 
HTML-страницы. 
3.2. Фреймворк и Django 
Фреймворк предоставляет готовую структуру и набор инструментов для разра-
ботки приложений. В отличие от библиотеки, которую программист вызывает из соб-
ственного кода, фреймворк сам управляет ходом выполнения программы, а разработ-
чик наполняет его своими модулями и обработчиками. 
Django – веб-фреймворк для Python, предназначенный для создания веб -прило-
жений. Django предоставляет средства для:

• маршрутизации URL;

• обработки форм;

3.3. Django-проект и Django-приложение 
Важно различать два понятия: 
• Django-проект – общая конфигурация системы: настройки, маршрутизация верх-
него уровня, точки запуска; 
• Django-приложение – функциональная часть системы, реализующая отдельную 
область. 
Django-проект содержит настройки и общую конфигурацию веб -приложения. 
Django-приложение предназначено для реализации отдельной функциональной обла-
сти. Например, для системы бронирования помещений в дальнейшем могут исполь-
зоваться приложения homepage, rooms и bookings.

Маршрутизация – процесс определения обработчика по адресу запроса. Когда

Маршрут описывается функцией path(): первый аргумент – шаблон адреса,

3.6. HTML, CSS и Bootstrap 
HTML – язык разметки гипертекста, описывающий структуру веб -страницы. 
HTML-документ состоит из двух основных частей: head (служебная информация: 
кодировка, заголовок вкладки, подключение стилей) и body (содержимое страницы). 
Основные элементы: заголовки h1–h6, абзацы p, списки ul/ol/li, ссылки a, таб-
лицы table. 
CSS – язык описания внешнего вида страницы. Селекторы определяют, к каким 
элементам применяются стили; свойства задают оформление: цвет, размер, отступы. 
Стили наследуются – свойства родительских элементов переходят к вложенным эле-
ментам. 
Bootstrap – CSS-фреймворк для быстрой верстки интерфейсов. Bootstrap  содер-
жит готовые компоненты (навигационная панель, кнопки, таблицы, карточки) и сетку 
для адаптивной верстки. В ПР5 используется актуальная версия Bootstrap 5.3, под-
ключаемая через CDN без установки дополнительных пакетов.

5.4.4. Первые view-функции 
View-функция – обычная функция Python, которая принимает объект запроса  
HttpRequest и возвращает объект ответа  HttpResponse. Первым аргументом 
view-функция всегда принимает request; если в шаблоне адреса использована пе-
ременная, она передаётся вторым аргументом. 
===== PAGE 19 =====
 
19 
HttpResponse принимает первым аргументом строку – текстовое содержимое, 
которое отобразится в браузере. Параметр status задаёт код ответа сервера (200 – 
успех, 404 – не найдено). 
View-функции хранятся в файле  views.py каждого приложения – по той же 
логике, что и urls.py. 
Первоначальная проверка маршрутизации выполняется view -функциями, воз-
вращающими короткие HttpResponse. Опишите в файлах views.py трёх прило-
жений следующие функции. В файле homepage/views.py: 
from django.http import HttpResponse 
 
 
def index(request): 
    return HttpResponse("Roomly – система бронирования помещений") 
В файле rooms/views.py: 
from django.http import HttpResponse 
 
 
def rooms(request): 
    return HttpResponse("Список помещений") 
 
 
def room_detail(request, room_id): 
    return HttpResponse(f"Помещение {room_id}") 
В файле bookings/views.py: 
from django.http import HttpResponse 
 
 
def bookings(request): 
    return HttpResponse("Список бронирований") 
 
 
def booking_detail(request, booking_id): 
    return HttpResponse(f"Бронирование {booking_id}") 
Данные функции являются первоначальной проверкой прохождения запроса по 
цепочке: браузер → URL → urls.py → view → response. Переносить всю 
функциональность консольного приложения в Django на этом этапе не требуется. 
Обратите внимание: функции room_detail() и booking_detail() прини-
мают второй аргумент – room_id и booking_id соответственно. Этот аргумент 
будет передан из URL в пункте 5.4.5, где в шаблонах адресов появятся переменные.

20 
Даже если view-функция не использует этот аргумент, она обязана его принять – 
иначе Django вернёт ошибку.

5.4.7. Обработка ошибки 404 
В разделе 5.4.5 упоминалось: если адрес не обнаружился ни в одном 
urlpatterns, пользователь получает страницу с ошибкой 404 Page Not Found. 
Пока DEBUG = True , Django показывает техническую страницу отладки: в ней пе-
речислены все маршруты проекта и причина, по которой ни один из них не подошёл. 
Такая страница помогает разработчику искать ошибку, но не предназначена для по-
сетителей сайта. Собственную страницу 404 можно проверить только при отключён-
ной отладке. 
Откройте файл roomly/settings.py и отключите режим отладки. Заодно за-
полните ALLOWED_HOSTS – при выключенной отладке Django принимает запросы 
только к адресам из этого списка: 
DEBUG = False 
ALLOWED_HOSTS = ["localhost", "127.0.0.1"] 
Значения localhost и 127.0.0.1 означают локальную машину – этого до-
статочно для проверки на встроенном сервере разработки. Если список оставить пу-
стым, Django при DEBUG = False ответит кодом 400 на любой запрос. 
Стандартная страница Django при отключённой отладке – короткая служебная 
надпись «Not Found» без оформления проекта. Чтобы показать собственную стра-
ницу, подключите обработчик handler404. Обработчик объявляется строкой с пу-
тём к view-функции и размещается в корневом urls.py на уровне модуля, рядом с 
urlpatterns: 
handler404 = "homepage.views.page_not_found"

Теперь добавьте в homepage/views.py view-функцию обработчика. Она со-

def page_not_found(request, exception): 
    content = """

Аргумент exception обязателен: при срабатывании обработчика Django пере-
даёт в него объект исключения, приведшего к ошибке. На странице он не отобража-
ется – значение используется для журналирования и сложных сценариев обработки. 
Механизм тот же, что и в room_detail(): ответ формируется с кодом статуса 404. 
Разница в том, что handler404 срабатывает автоматически для любого адреса, ко-
торому не нашлось маршрута, – отдельный код в каждой view-функции не требуется. 
Страница обработчика вызывается не только при отсутствии маршрута. Если 
view-функция возбудит исключение Http404 из модуля django.http, Django пе-
рехватит его и также покажет страницу 404. В этом проекте несуществующие объ-
екты обрабатываются явным возвратом HttpResponse со статусом 404 
(room_detail() в разделе 5.4.8) – оба способа корректны, выбор зависит от задачи. 
Примечание. Настраивать обработку ошибки 404 в каждом приложении отдельно не требу-
ется. Параметр handler404 читается только из корневого urls.py проекта, поэтому обработчик 
объявляется один раз и действует для всех приложений сразу: Django перехватывает исключение 
Http404, возбуждённое в view-функции любого приложения, и показывает страницу обработчика. 
На уровне отдельного приложения остаётся лишь решить, когда запрошенные данные считаются не 
найденными, и сообщить об этом – возбудить Http404 или вернуть ответ со статусом 404, как 
room_detail() приложения rooms. Объявление handler404 внутри urls.py приложения не 
действует: Django игнорирует его и использует только обработчик из корневого модуля маршрути-
зации. 
Сохраните изменения и откройте в браузере заведомо несуществующий адрес, 
например http://127.0.0.1:8000/nonexistent/. Вместо технической стра-
ницы отладки отобразится собственная страница проекта: заголовок, пояснение и 
кнопка возврата на главную. 
Примечание. В режиме разработки значение DEBUG = True  обычно сохраняют: техниче-
ские страницы ошибок упрощают поиск проблем. Проверив собственную страницу 404, верните 
DEBUG = True – настройка handler404 сохранится и заработает на рабочем сервере, где режим 
отладки отключён. Кроме того, при DEBUG = False  встроенный сервер разработки не раздаёт 
статические файлы проекта.

def find_booking_by_id( 
    bookings: List[Booking], 
    booking_id: int, 
) -> Optional[Booking]: 
    """Найти бронирование по идентификатору.""" 
    for booking in bookings: 
        if booking.id == booking_id: 
            return booking 
    return None

Основные методы: 
* `__str__()` – строковое представление пользователя; 
* `from_data()` – создание объекта `User` из набора данных. 
 
### Booking – бронирование 
 
Объект `Booking` представляет бронирование помещения пользователем. 
 
Основные атрибуты: 
* `id` – уникальный идентификатор бронирования; 
* `room` – объект `Room`; 
* `booking_date` – дата бронирования; 
* `user` – объект `User`; 
* `is_cancelled` – признак отмены бронирования. 
 
Основные методы: 
* `cancel()` – отмена бронирования; 
* `__str__()` – строковое представление бронирования.
